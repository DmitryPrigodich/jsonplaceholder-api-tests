# Как объяснить проект на собеседовании

## Краткое описание

«Это набор API-тестов для JSONPlaceholder на pytest и requests. Я разделил HTTP-транспорт,
методы ресурсов, схемы данных и проверки, чтобы сценарии читались как действия пользователя API.
Есть отдельные smoke и full наборы, параметризация, негативные случаи, настройка base URL,
таймауты, retries, HTML-отчёт и CI. Особенности учебного API описаны явно».

Перед встречей стоит самостоятельно выполнить команды из README, открыть отчёт и пройти
путь одного теста от fixture до HTTP-запроса и проверки. Объяснять решения нужно своими словами.

## Путь одного теста

На примере `test_create_post`:

1. `post_payload` создаёт валидный `PostPayload` для текущего теста.
2. `posts_api` предоставляет объект `PostsApi`, использующий общий `ApiClient`.
3. `create()` сериализует DTO с именем поля `userId` и вызывает `POST /posts`.
4. `ApiClient` отправляет запрос через `requests.Session` с заданными таймаутами и логированием.
5. Тест проверяет HTTP 201, JSON, строгую схему `Post`, положительный ID и совпадение полей.
6. HTML-отчёт получает результат; сессия HTTP закрывается после завершения прогона.

## Почему такие компоненты

**pytest.** Fixtures управляют жизненным циклом объектов, parametrization сокращает повторение,
markers позволяют выбирать набор, а встроенная диагностика `assert` помогает разбирать ошибки.

**requests.** Сценарии последовательные, поэтому асинхронность не нужна. Session повторно
использует соединения. Для параллельного запуска потребовались бы отдельные сессии на worker,
а не совместное использование одного Session между потоками.

**Pydantic.** Проверяет вложенную структуру пользователя и типы полей всех ответов.
Строгий режим предотвращает незаметное преобразование строки в число.
Дополнительные поля ответа разрешены, чтобы совместимое расширение API не ломало тесты.

**pytest-html.** Даёт один открываемый HTML-файл без установки Java и сервера отчётов.
Для этого задания достаточно; Allure был бы альтернативой при необходимости развитых
вложений, шагов и истории результатов.

**Простая композиция.** Один транспорт и три класса ресурсов. Абстрактные базовые классы
и универсальный CRUD-конструктор не добавлены: сейчас они усложнили бы чтение без пользы.

## Что проверяется помимо статуса

- Наличие и корректность JSON Content-Type и самого JSON.
- Обязательные поля, вложенные объекты и типы через модели.
- Совпадение ID запрошенного ресурса с ответом.
- Совпадение отправленных и возвращённых полей при записи.
- Сохранение других полей при PATCH.
- Связь комментариев с нужным постом и результатов фильтрации с пользователем.
- Непустые ожидаемые коллекции и отсутствие повторяющихся ID.

Не проверяется точный текст каждого существующего поста: это сделало бы набор зависимым
от содержимого фикстур стенда, а не от нужного поведения API.

## Главная особенность негативных тестов

JSONPlaceholder принимает неверные данные и возвращает 201. Не стоит утверждать, что API
имеет полноценную валидацию, или писать тесты на выдуманный ответ 400.

В проекте сохранено желаемое ожидание 400/422, а шесть известных случаев отмечены строгим
`xfail` с узким типом исключения. Если сервер вернёт 503, это будет настоящее падение.
Если валидацию исправят, `XPASS(strict)` потребует удалить устаревший маркер.
Команда `python -m pytest -m contract --runxfail` показывает проблемы без обработки xfail.

DTO не блокируют отправку неверных данных: API-методы также принимают raw dict и `None`.
Иначе получилось бы тестирование клиентской валидации вместо серверной.

## Почему нет CRUD-цепочки

У JSONPlaceholder операции записи имитируются и не сохраняются.
Созданный пост нельзя надёжно прочитать последующим GET; удалённый пост остаётся доступен.
Поэтому каждый тест независим и проверяет реальный контракт ответа своей операции.

В API с постоянным хранилищем понадобятся создание уникальных данных, проверка чтением
и cleanup в `yield` fixture / finalizer, включая случай падения теста.

## Почему retries ограничены

Повторы применяются на уровне HTTP-транспорта, а не к тестам с упавшими assertions.
GET можно безопасно повторить после временной ошибки. Повтор записи после read timeout
опасен: сервер мог уже выполнить запрос, а клиент просто не получил ответ.
Поэтому повтор HTTP-ошибок и ошибок чтения включён только для GET/HEAD/OPTIONS.
Ошибка соединения до отправки запроса допускает повтор для любого метода.

Проверки через локальный HTTP-сервер подтверждают поведение настоящих requests/urllib3:
GET повторяется, запись после 503 — нет, 400 не повторяется, таймаут срабатывает,
а исчерпание retries не скрывает последний 503.

## Как масштабировать

Для нового ресурса добавить API-класс и модель, затем fixture и тесты.
Однотипные случаи оформлять параметрами с понятными `id`.
Переиспользовать общие проверки, но не прятать смысл сценария в универсальные функции.

При росте набора можно разделить `api.py` и `models.py` на модули по ресурсам,
добавить отдельные окружения и запуск workers с изолированными данными.
Параллельную нагрузку на публичный стенд в этом проекте специально не создаём.

## Что показать на демонстрации

```bash
python -m pytest -m smoke
python -m pytest -m full
python -m pytest -m unit
python -m pytest -m contract --runxfail
```

Последняя команда намеренно завершается с ошибкой: она демонстрирует ограничения валидации.
После неё можно снова запустить обычный набор, чтобы получить итоговый HTML-отчёт.
На Windows без активации окружения вместо `python` использовать `.\.venv\Scripts\python.exe`.
